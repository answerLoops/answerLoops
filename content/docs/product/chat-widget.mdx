The answerLoops chat widget adds a support chatbot to any website or documentation site that accepts custom JavaScript. Visitors ask questions about your community, business, or product and get answers from your published knowledge-base articles, without creating an account.

<Callout type="info" title="Availability">
  The widget is included on every hosted plan and on self-hosted installs. The Standard plan shows a "Powered by answerLoops" line; Pro and Enterprise can remove it and also capture unanswered widget questions in the [Review queue](/docs/product/knowledge-base#review-queue). Each widget answer counts toward your plan's monthly deflection allowance. See [Billing plans](/docs/reference/billing-plans).
</Callout>

The widget answers from **published knowledge-base articles only**. Unlike your connected channels, it does not draw on past resolved tickets. Those are written for the one person who raised them and often contain account details or internal notes, and a widget visitor is anonymous.

<Callout type="warn" title="Thin knowledge, thin answers">
  A workspace with an empty knowledge base gets thin widget answers. Promoting a few resolved tickets into the knowledge base is what makes the widget useful, and it is the same step that generalises an answer so it is safe for anyone to read.
</Callout>

## Set it up

<Steps>
  <Step>
    ### Allow your domain

    Go to **Settings → Widget** and add your website or documentation domain under **Allowed domains**, then select **Save domains**. See [Restricting where the widget works](#restricting-where-the-widget-works).

    **What you should see:** the domain listed under Allowed domains. Until at least one domain is listed, the widget will not load on any site.
  </Step>
  <Step>
    ### Copy the embed snippet

    In the same **Widget** tab, copy the embed snippet. It looks like this:

    ```html
    <script src="https://your-instance.example.com/widget.js" data-widget-id="..."></script>
    ```
  </Step>
  <Step>
    ### Paste it into your site

    Paste it into your site's HTML before the closing `</body>` tag, or follow the steps for your platform below.

    **What you should see:** a chat bubble at the bottom right of pages where you installed the snippet. Visitors select it to open the chat panel.
  </Step>
  <Step>
    ### Preview and test

    Select **Preview widget** in Settings to try it without any extra configuration, then ask a question your articles cover. Open **Knowledge Base → Knowledge coverage** (also linked from **Settings → Widget**) to see exactly which articles the widget can answer from.

    **What you should see:** an answer drawn from your articles. If the panel instead says the widget is not enabled for a domain, add that domain under Allowed domains.
  </Step>
</Steps>

## Adding it by platform

Where you paste the snippet depends on how your site is built. Find your platform below.

<Tabs items={['Wix', 'Squarespace', 'Shopify', 'WordPress', 'Webflow', 'Next.js', 'React / Vite', 'Angular', 'npm package']}>
  <Tab value="Wix">
    Settings → Custom Code → add code → paste the snippet → set it to load on **all pages**, placement **Body - end**.
  </Tab>
  <Tab value="Squarespace">
    Settings → Advanced → Code Injection → paste the snippet into the **Footer** field → Save.
  </Tab>
  <Tab value="Shopify">
    Online Store → Themes → **Edit code** → open `theme.liquid` → paste the snippet right before `</body>` → Save. One edit covers every page.
  </Tab>
  <Tab value="WordPress">
    Install a header/footer plugin (e.g. "Insert Headers and Footers"), paste the snippet into the **footer** field, and save. Avoids hand-editing `footer.php`, which a theme update can overwrite.
  </Tab>
  <Tab value="Webflow">
    Project Settings → Custom Code → paste the snippet into **Footer Code** → Save → Publish. Custom code only takes effect after a publish, not just a save.
  </Tab>
  <Tab value="Next.js">
    Load it once from the file that wraps every page, using `next/script` so it doesn't block rendering.

    **App Router** — `app/layout.tsx`:
    ```tsx
    import Script from 'next/script'

    export default function RootLayout({ children }: { children: React.ReactNode }) {
      return (
        <html lang="en">
          <body>
            {children}
            <Script
              src="https://your-instance.example.com/widget.js"
              data-widget-id="..."
              strategy="lazyOnload"
            />
          </body>
        </html>
      )
    }
    ```

    **Pages Router** — `pages/_app.tsx`:
    ```tsx
    import Script from 'next/script'
    import type { AppProps } from 'next/app'

    export default function App({ Component, pageProps }: AppProps) {
      return (
        <>
          <Component {...pageProps} />
          <Script
            src="https://your-instance.example.com/widget.js"
            data-widget-id="..."
            strategy="lazyOnload"
          />
        </>
      )
    }
    ```
  </Tab>
  <Tab value="React / Vite">
    Paste the raw snippet into `public/index.html`, before `</body>` — this is the one file the bundler doesn't compile, so it behaves like a plain static site:
    ```html
    <script src="https://your-instance.example.com/widget.js" data-widget-id="..."></script>
    ```
  </Tab>
  <Tab value="Angular">
    Paste the raw snippet into `src/index.html`, before `</body>` — Angular's static app shell, equivalent to Vite's `index.html`:
    ```html
    <script src="https://your-instance.example.com/widget.js" data-widget-id="..."></script>
    ```
  </Tab>
  <Tab value="npm package">
    For a React or Next.js app you can install the widget as a dependency instead of pasting a script tag. It loads the same widget from your instance, so your branding, allowed domains and knowledge base apply unchanged.

    ```bash
    npm install @answerloops/widget
    ```

    Place the component once, in the layout that wraps every page:
    ```tsx
    import { AnswerLoopsWidget } from '@answerloops/widget/react'

    <AnswerLoopsWidget
      widgetId="<your-embed-token>"
      baseUrl="https://your-instance.example.com"
    />
    ```

    Outside React, call `mountWidget({ widgetId, baseUrl })` from `@answerloops/widget`; it returns a handle with an `unmount()` method. Use the same embed token and instance address as the snippet in **Settings → Widget**.
  </Tab>
</Tabs>

<Note>
  Whichever platform you use, the rule is the same: paste into the **one file or field that wraps every page** (a layout, an app shell, a footer-code field) — never a single page's content, or the widget only loads there.
</Note>

## What you can customize

| Setting | Where | Notes |
|---|---|---|
| Branding | **Settings → Widget** | Standard shows the answerLoops logo and a "Powered by answerLoops" line. Pro and Enterprise can remove the answerLoops branding; **Settings → Widget** shows an upgrade option when your plan does not include it. Self-hosted installs have it unlocked. |
| Allowed domains | **Settings → Widget** | The domains the widget may load on. Subdomains are included. |
| Embed token | **Settings → Widget** | Issued per workspace and expires after 90 days; **Regenerate token** issues a new one. |
| Ask for an email | **Settings → Widget** | When the widget collects a visitor's email address: only after an unanswered question (default), before the conversation starts, or never. |
| What it knows | **Knowledge Base** | Publish or unpublish articles and sources. The widget only answers from published articles. |
| Contact and link cards | Your articles | Cards show links and contact details only when they are written in your articles. There is nothing to configure. |

The chat bubble sits at the bottom right of the page, and the answer language follows the visitor's language. Neither is configurable.

## Restricting where the widget works

The `data-widget-id` value is an **embed token**, and it is deliberately public: it ships in the HTML of every page the widget renders on. Because anyone can read it, **Settings → Widget → Allowed domains** is how you control where the widget works. List the domains you embed on, one per line:

```
example.com
docs.example.com
```

Subdomains of a listed domain are included, so `example.com` also covers `support.example.com`. Ports are ignored. Embeds on any other domain show a short message explaining that the widget is not enabled there, rather than failing silently.

<Callout type="warn" title="The widget will not load until you list a domain">
  The widget will not load anywhere until you list at least one domain. Your own answerLoops domain is always permitted, so the **Preview widget** link in Settings works without any configuration.
</Callout>

If the panel says it could not confirm which site it is embedded on, the page is blocking referrer information; loading the page over HTTPS usually resolves it.

Only workspace owners and admins can change the allowed domains or regenerate the token. Members can see the embed snippet but not alter where it works. Usage limits apply independently of the allowlist.

### Documentation sites

If your docs run on a platform that executes custom JavaScript on every page — Mintlify, Docusaurus, and most others do — you can mount the widget there without editing templates. Drop a small script that injects the snippet, and add the docs domain to your allowed domains.

This is usually the highest-value place to put it: docs visitors are anonymous and arrive with support-shaped questions, which is exactly what the knowledge base answers.

<Note>
  On platforms with no build step, the embed token ends up committed to whatever repository holds your docs. The token is a public identifier rather than a secret, but rotating it then requires a commit.
</Note>

## Lead capture

**Settings → Widget → Ask for an email** controls whether, and when, the widget asks a visitor for their email address.

- **Only if it can't help** (default) — the visitor goes straight into the conversation. The widget only asks for an email after a turn it couldn't really answer: no knowledge-base article matched the question, or the visitor explicitly asked to talk to a person. The ask appears inline, right under that answer, with a short line explaining why ("I couldn't find anything on that — leave your email and someone will follow up"), and a **No thanks** option that lets the visitor keep chatting without it. It only appears once per conversation.
- **Before the conversation starts** — the visitor sees an email field before they can ask anything, with a **Skip** link to bypass it.
- **Never** — the widget never asks.

<Callout type="info" title="Why the default changed">
  Asking up front, before the widget has done anything to earn the visitor's trust, was costing more conversations than the leads it produced — a visitor arrives with a question, not an intent to hand over an email, and bounces rather than answer a stranger-bot. Asking after a real miss gives the visitor context for why they're being asked, and the resulting address is attached to an actual unresolved question rather than a cold form fill.
</Callout>

## Rotating the token

Tokens expire after **90 days**. Settings warns you as the date approaches, and **Regenerate token** issues a new one.

<Callout type="warn" title="Rotating takes effect immediately">
  Regenerating invalidates the old token. Every page still using the old snippet stops working until you update it. Rotate when you are able to update your site, not before.
</Callout>

## Rich answer cards

Besides text, the assistant can answer with a small set of prebuilt cards when one is clearer than a paragraph:

- **Steps** — a numbered how-to for setup and troubleshooting sequences.
- **Quick replies** — tappable options when a question is ambiguous. Tapping one sends it as the visitor's next message.
- **Callout** — a highlighted tip, warning or confirmation.
- **Link card** — a card pointing to a page from your knowledge base.
- **Contact options** — email, phone or support-page buttons when a visitor needs a person.

The assistant only fills in the content of these cards; it never produces markup or code, and the widget draws every card with its own components, so cards match the widget's look and work on mobile. Links and contact details only appear in a card when they are written in your knowledge base articles — the assistant can't invent a URL, email address or phone number. Links must be `https`, and they open in a new tab. If a card's content doesn't pass those checks, the widget shows nothing for it and the text answer stands on its own.

To get contact or link cards, put the addresses and URLs you want visitors to see in your knowledge base articles. There is nothing to configure.

## Rate limits and input caps

The widget chat endpoint is public (no login required), so it enforces limits to protect your AI provider bill from abuse:

- Up to **100 requests/minute per widget token** (caps total cost exposure for one site even if traffic comes from many IPs)
- Up to **20 requests/minute per visitor** (token + IP combination)
- Up to **500 answers/hour and 3,000 answers/day per workspace**, across all visitors and widget tokens
- Loading the widget panel itself is limited to **30 loads/minute per visitor address** and **600/minute per widget token**
- Each message capped at **4,000 characters**; at most **50 messages** per request
- Request bodies capped at **512KB**

The lead-capture endpoint, used when a visitor leaves an email address, is limited separately at **30/minute per token** and **5/minute per visitor**, with a 64KB body cap and a validated address.

The on-failure check — a small lookup the widget makes right after a turn finishes, to decide whether to show the lead-capture prompt — is limited at **100/minute per token** and **20/minute per visitor**, the same shape as the chat endpoint next to it.

Requests over these limits return `429 Too Many Requests`. The chat and lead-capture limits are enforced across every running instance rather than per process, so those numbers are the real ceiling. The on-failure check's result, by contrast, is held in the memory of whichever instance answered the chat request — see Lead capture above — so on a multi-instance deployment a visitor's next poll can land on a different instance and simply see no prompt for that turn; nothing breaks, the prompt just doesn't appear. None of these limits are currently configurable.

Separately from rate limits, every widget answer counts toward your plan's monthly deflection allowance. On Standard, the widget stops answering once the allowance is used up and resumes at the next calendar-month reset; Pro keeps answering and bills overage. See [Billing plans](/docs/reference/billing-plans).

## What the widget can and cannot reach

It answers from your **knowledge base** — published articles only. It does not read your ticket queue, and it has no access to settings, billing, or team data either; the embed token grants none of those.

Treat knowledge base contents as visible to anyone who can use the widget. If you have ingested internal documentation, review it before making the widget public.

title: Knowledge Base
description: Import, manage, and search your knowledge base so the AI can deflect questions accurately.

answerLoops searches the knowledge base for material relevant to a question and uses it to draft a reply. Keep articles current and review imported content before using it for customer answers.

## Import methods

There are four ways to add content to the knowledge base. URL import and file upload embed each chunk for search. On a hosted plan this works without your own AI key, using your workspace's included AI usage; if that is used up for the month, the import stops with a message asking you to add your own provider under **Settings → AI Model**.

If the embedding model behind your knowledge base changes, answerLoops re-embeds your content in the background from what you already added. Search keeps working throughout, and you don't need to re-upload anything. An article you edit while the re-index runs is processed again before it goes live, and the re-index stops with a clear message if the chosen embedding model produces vectors of a size the knowledge base can't store.

### 1. URL import

Import a web page or an entire documentation site.

1. Go to **Knowledge Base → Import**
2. Paste a URL into the import field
3. Choose **Single page** or **Entire site**
   - Single page imports only that URL
   - Entire site crawls linked pages up to a maximum of **25 pages**
4. Click **Import** and wait for processing to finish. Larger sites take longer.
5. Imported pages appear in the Sources list when complete

Each page becomes a separate source entry. The crawler fetches the rendered content, splits it into chunks, embeds each chunk as a vector, and writes everything to the database.

**Addresses:** imports accept public web addresses only (`http` or `https`). If the address cannot be found, the import stops with a message asking you to check it. Pages on a site that cannot be imported are left out.

**Import limits:** one import run saves at most 150 sections and about 600,000 characters in total across all of its pages, not per page. If a site import reaches that limit, the pages not yet reached stay un-imported and the next run continues from them. Section titles are shortened to 300 characters. Each workspace holds up to 2,000 articles.

If an import fails before any section is saved, no source is left behind, so you can run the same import again.

**Re-import deduplication:** if you import the same URL a second time, pages that were already ingested are skipped automatically. Only new pages are processed. This means you can safely re-run a site import after adding new docs without creating duplicates.

<Note>
  Self-hosted operators must configure the URL import service. See [environment variables](/docs/self-hosting/environment-variables#url-ingest--firecrawl-optional).
</Note>

### 2. File upload

Drag and drop files directly into the KB.

**Supported formats:** PDF, DOCX, MD, TXT, CSV

**Maximum file size:** 10 MB per file

**Limits:** the text extracted from a file can be at most 2 MB, and PDFs can have up to 300 pages. Files that are too large or too complex to read are rejected with a message saying so. File names are shortened to their base name (up to 200 characters). Only workspace owners and admins can upload files.

1. Go to **Knowledge Base → Import**
2. Drag files onto the upload area, or click to open the file picker
3. Files are processed immediately — each becomes one or more source entries depending on size

Large files are split into chunks automatically. Each chunk is embedded and indexed for semantic search. If no chunk can be saved, the file's source entry is removed so you can upload the file again.

### 3. GitHub repo sync

Connect a GitHub repository and sync its markdown files into the KB.

1. Go to **Knowledge Base → GitHub Sync**
2. Select the repository from the picker (requires GitHub App installed on your org)
3. Click **Sync now** to queue an import of all `.md` and `.mdx` files
4. Optionally enable **Auto-sync on push** — answerLoops receives a webhook from GitHub on every push to the default branch and queues a re-sync automatically

The sync respects the repo's file tree. Each markdown file becomes its own source entry.

GitHub and Notion syncs run as background jobs — the Knowledge Base page shows each one as queued, then `Syncing N/M` as it works through the files or pages, then done, and you can navigate away while it runs. Re-triggering a sync for the same source while one is still in progress does nothing; the running job finishes on its own. Each sync builds its replacement alongside the live content and swaps it in only when complete, so a failed sync leaves your existing content in place. Starting a sync, deleting a source, toggling a source's publish state and deleting an article require an owner or admin role.

<Note>
  Install the GitHub App for the repositories you want to sync. Self-hosted operators must also configure the app credentials; see [GitHub setup](/docs/integrations/github).
</Note>

### 4. Notion workspace

Connect a Notion workspace and pull its pages and databases into the KB — useful for teams that keep their support content in Notion rather than a published docs site. Unlike the other three sources, this isn't one click: Notion requires creating a credential in Notion itself, then separately sharing pages with it. Full walkthrough with every click: [Notion integration](/docs/integrations/notion).

1. In Notion, create a connection (**Settings → Developer → Open developer tools → + New connection**, **Access token** auth) and copy its token (starts with `ntn_` or `secret_`).
2. Share the pages you want synced: open each top-level page, click **•••  → Connections**, and add your connection. Sharing a page also shares its subpages, so sharing one top-level parent page is usually enough rather than adding every page individually. answerLoops syncs everything the connection can see — you control the scope by sharing or unsharing pages in Notion.
3. In answerLoops, go to **Integrations → Notion**, paste the token, and click **Connect**.
4. Go to the **Knowledge Base** page and click **Sync now** in the Notion panel. Each Notion page (and each row of a shared database) is converted to text, split into chunks, and embedded like every other source. Re-syncing replaces the previous Notion content.

<Note>
  Notion content imports **unpublished**. It is searchable from the dashboard but is not used to answer customer questions or served to the website widget until you click **Publish to widget** on the Notion panel. Every other source publishes automatically on import; Notion is the exception because workspace docs are often internal drafts. Your publish choice is kept across re-syncs.
</Note>

The token is stored encrypted (set `ENCRYPTION_KEY` before connecting in any real deployment). There is no environment variable to configure — Notion is set up per workspace in the Integrations UI.

## Sources list

The **Manage** tab on the Knowledge Base page lists every imported source. Each row shows:

| Column | Description |
|---|---|
| **Name** | File name, page URL, repo, or "Notion workspace" |
| **Type** | `url`, `file`, `github`, or `notion` |
| **Chunks** | Number of vector chunks indexed from this source |
| **Size** | Approximate content size |

A source marked **Unpublished** (currently only Notion) is indexed and shows in dashboard search but is held back from customer-facing answers and the website widget until you publish it from the Notion panel.

To remove a source, select it and click **Delete selected**. Deleting a source removes all its chunks from the vector index — any articles derived from it will no longer surface in search results.

## Adding knowledge by hand

Not everything the assistant should know comes from a ticket or a file. Product details, policies, and "how we actually do it" answers often live in someone's head. The **Write an answer by hand** form at the top of the Manage tab lets you write them down directly.

1. Enter a **question or title**, such as "Do you ship to Canada?"
2. Write the **answer or context** the way you would tell a customer.
3. Click **Add to knowledge base**.

The article is published immediately, so the assistant can use it for the very next question. There is no draft step, which means anything you write is visible to customers through the assistant: leave out names, account details, and anything internal. If you want a second pair of eyes first, use the [Review queue](#review-queue) instead.

Things to know:

- Only workspace **owners and admins** can add articles this way.
- The question or title can be up to 500 characters and the answer up to 8,000.
- Articles added by hand appear on the **Knowledge coverage** tab under **Added by hand**, and you can delete them from the article list like any other.
- Adding needs an AI provider, because each article is indexed for search when it is saved. If none is connected, the form tells you to add one in **Settings → AI Model**.
- Adds are limited to 30 every 10 minutes per workspace, and a workspace holds up to 2,000 articles in total.

## Promoting tickets to the KB

When a ticket is resolved with a good answer, you can turn it into a KB article so the AI can reuse that answer for similar future questions.

1. Open a ticket with status `resolved`
2. Click **Promote to KB** in the ticket actions panel
3. The Q&A pair is saved as a new KB article

Promoted articles appear in the Sources list with type `ticket`.

## Search

Use the search bar at the top of the Knowledge Base page to find articles.

**Semantic search** (default when an AI provider is configured or included usage is available): searches by meaning rather than exact words. Asking "how do I reset my password" will surface an article titled "Account recovery steps" even though the words don't match exactly.

**Keyword fallback** (when no AI is available, for example included usage is used up and no key is configured): falls back to exact text matching. An amber warning banner appears at the top of the KB page to indicate that semantic search is unavailable.

To clear a search and return to the full article list, click the **×** inside the search field or the **Clear** button.

## Knowledge coverage

The **Knowledge coverage** tab shows exactly what your chat assistant is able to answer from, so nobody is surprised by what it does or doesn't know. You can also reach it from **Settings → Widget**.

- **Counts.** Live articles, sources, and any articles the assistant can't use.
- **Titles by source.** Every article title, grouped by where it came from: each uploaded file or imported page, synced sources, tickets you promoted, and articles added by hand.
- **Status per article.** An article is **live** when it is published and searchable. **Unpublished** articles are kept private and are not used by the assistant unless you publish them. This is the right state for internal documents, such as a Notion workspace you only want your team to see. **Not searchable** articles are missing a search index entry (usually because embedding failed during import) or were indexed with an embedding model other than the one your workspace currently uses, so the assistant cannot find them yet. Articles on an older model are re-indexed automatically after you switch models; for a failed import, re-import the source.
- **Try a customer question.** Type a question and the tab runs the same lookup the chat widget uses. It shows which articles the assistant would draw on, with a match score, or tells you that nothing covers the question. If semantic search is unavailable, it says so instead of guessing.

If a question doesn't closely match any live article, the assistant answers from general knowledge instead, and that answer can be wrong. Use the tab to find those gaps before your customers do, then add or edit an article to cover them. The tab is available on every plan.

## Review queue

The **Review** tab turns questions your knowledge base couldn't answer into new articles, with a person checking every one before it goes live. It is available on the Pro plan and above.

When the assistant answers a question that nothing in your knowledge base (or your team's earlier answers) covered, the question lands in the queue instead of disappearing:

- **Support tickets** from your connected channels are added after the assistant has replied, so capturing a question never delays an answer. If the assistant's draft fully answered the question, it comes along as a starting point. If it didn't, the item is marked **No usable answer** and you write one.
- **Website chat widget** questions are added when no article matched. The widget keeps no record of who asked, so the queue shows the question and the answer the assistant gave, never the visitor. Email addresses, phone numbers and long digit runs are replaced with markers before the text is stored, and widget items are labelled as visitor-supplied text.

When the same question comes in again, the existing item's counter goes up (**Asked 4 times**) instead of adding a duplicate, and the most-asked questions are listed first. Items you reject stay rejected, and their count keeps rising so you can see if people keep asking.

For each item you can:

1. Edit the **question** and the **answer**. Remove names, account details and anything else that was only meant for the person who asked.
2. Click **Approve and add to knowledge base**. The edited text is saved as a new article and starts answering questions straight away.
3. Or click **Reject** to dismiss it. A rejected item can be moved back to review at any time.

Nothing in the queue is searchable or shown to customers until you approve it. The queue is visible to owners and admins only, because items contain text typed by customers and visitors; other team members see a short notice on the tab. The **Review** tab shows how many items are waiting, and each workspace holds up to 500 unreviewed items at a time. When the queue is full the tab says so and new questions are not captured, so clear it regularly.

The text of rejected items is removed, and the text of approved items is removed 90 days after review (the approved article keeps its own copy). The item and its counter stay so a repeated question is still recognised.

Approved articles count toward the same 2,000-article limit as every other source. The limit holds even when several people add articles at the same moment: once a workspace is full, further adds and approvals are declined with a message, and a declined approval stays in the queue.

## How the assistant uses your articles

Matching articles are passed to the assistant as reference material to answer from. This is the same whether the question arrives through the widget, a channel, email, or the Agent API and MCP `generate_answer`.

## Article usage

answerLoops keeps a count of how many answers each article was used for. An article is counted when it was among the matches handed to the assistant as context for an answer that was actually produced: a reply in the website chat widget, a drafted reply to a support ticket, a Discord `/ask` answer, or an answer generated through the Agent API. Searching the knowledge base, running a [simulation](/docs/product/simulation), and bug reports or feature requests (which are never answered from the knowledge base) are not counted.

Two things to keep in mind when reading the numbers:

- The count means the article was given to the assistant, not that the reply quoted it. The assistant decides what to use.
- Only a number per article per day is stored. The question, the visitor and the ticket are never recorded with it.

Deleting an article, or deleting the workspace, removes its counts.

## Data persistence

KB articles and source chunks are stored in the `kb_articles` and `kb_sources` tables in PostgreSQL. Questions waiting in the review queue are stored in `kb_review_items` until they are approved or rejected, and the per-article answer counts are stored in `kb_article_usage`. They persist across Docker restarts as long as you retain the `postgres-data` volume.

<Warning>
  Never run `docker compose down -v`. The `-v` flag deletes all Docker volumes, which permanently removes your KB articles, tickets, and all other data. Use `docker compose down` (without `-v`) to stop the stack safely.
</Warning>

The knowledge base is the material answerLoops answers from. When a question arrives, answerLoops searches your articles for the ones closest in meaning and hands them to the AI as reference material for the reply. Better, fresher articles mean more questions the AI can answer on its own.

Open **Knowledge Base** from the **Improve** group in the sidebar. The page has three tabs: **Manage** (add and organize content), **Knowledge coverage** (see what the assistant can answer from), and **Review** (turn unanswered questions into articles).

## How it fits together

1. **You add content.** Import a web page or site, upload a file, sync a GitHub repository or a Notion workspace, write an answer by hand, or promote a resolved ticket.
2. **answerLoops makes it searchable.** Each source is split into sections. Each section becomes one article, and every article is converted into an embedding, a numeric fingerprint of its meaning, so it can be found by meaning rather than exact words.
3. **The assistant draws on it.** For each question, the closest articles are passed to the assistant as reference material. This works the same whether the question arrives through the widget, a channel, email, or the Agent API and MCP `generate_answer`.
4. **You close the gaps.** Questions the knowledge base could not answer land in [Knowledge Gaps](/docs/product/knowledge-gaps) and the Review queue, ready to become new articles.

On a hosted plan, creating embeddings works without your own AI key, using your workspace's included AI usage. If you reach this month's limit, the import stops with a message asking you to add your own provider under **Settings → AI Model**.

## Add content

Pick the method that matches where your knowledge already lives. Importing, uploading, and syncing are for owners and admins.

<Tabs items={['Web page or site', 'File upload', 'GitHub repository', 'Notion workspace']}>
  <Tab value="Web page or site">
    Best for a public help center or documentation site. Importing reads each page, splits it by its headings, and saves each section as an article.

    <Steps>
      <Step>
        On the **Manage** tab, find the **Import from URL** panel.
      </Step>
      <Step>
        Paste a public `http` or `https` address, such as `https://docs.example.com`.
      </Step>
      <Step>
        Choose **Single page** to import only that address, or **Entire site** to follow links across the site (up to 25 pages per run).
      </Step>
      <Step>
        Click **Import** and wait. Larger sites take longer, and a progress message tells you what stage it is in.
      </Step>
    </Steps>

    Each page becomes its own entry in the Sources list. When you import a URL again, pages already imported are skipped and only new ones are processed, so you can safely re-run a site import after adding new docs. If a run stops short of the whole site, the result message tells you to click **Import** again to continue.

    If the address cannot be found, the import stops with a message asking you to check it. If an import fails before anything is saved, no source is left behind, so you can simply run it again.

    <Callout>
      Self-hosted operators must configure the URL import service. See [environment variables](/docs/reference/environment-variables#knowledge-base-crawling).
    </Callout>
  </Tab>
  <Tab value="File upload">
    Best for PDFs, exported documents, and notes that live on someone's computer.

    <Steps>
      <Step>
        On the **Manage** tab, find the **Upload file** panel.
      </Step>
      <Step>
        Drag a file onto the upload area, or click it to open the file picker.
      </Step>
      <Step>
        Wait for **Parsing and embedding**. Large files can take 15 to 60 seconds. The result tells you how many chunks were added.
      </Step>
    </Steps>

    Supported formats are PDF, DOCX, MD, TXT, and CSV, up to 10 MB per file. Each file is split into sections and every section is indexed for search. If nothing from the file can be saved, its source entry is removed so you can upload the file again.

    <Callout>
      Files that are too large or too complex to read are rejected with a message saying so. The text extracted from a file can be at most 2 MB, and a PDF can have up to 300 pages.
    </Callout>
  </Tab>
  <Tab value="GitHub repository">
    Best for open-source projects and teams that keep docs next to the code. The Markdown files in a repository, and its answered GitHub Discussions, become articles.

    <Steps>
      <Step>
        Install the GitHub App for the repository. Self-hosted operators also need to configure the app credentials; see [GitHub setup](/docs/integrations/github).
      </Step>
      <Step>
        In **Integrations → GitHub**, switch on **Knowledge Base** for the repository.
      </Step>
      <Step>
        Back on the **Manage** tab, the repository now appears under **GitHub Repositories**. Click **Sync now**.
      </Step>
    </Steps>

    A sync reads up to 100 `.md` and `.mdx` files from the repository. It skips folders such as `node_modules`, `vendor`, `.github`, `test`, `tests`, `__tests__`, and `spec`, plus `CHANGELOG`, `LICENSE.md`, and `CODE_OF_CONDUCT.md`. The whole repository is one entry in the Sources list, and its answered Discussions are a second one (type `github-discussion`).

    With **Knowledge Base** switched on, answerLoops also re-syncs automatically on every push to the default branch, and a Discussion is added the moment it is marked as answered.
  </Tab>
  <Tab value="Notion workspace">
    Best for teams that keep support content in Notion rather than on a published docs site. This one is not a single click: Notion needs a credential created in Notion itself, and you then share pages with it. The full walkthrough is in the [Notion integration](/docs/integrations/notion) guide.

    <Steps>
      <Step>
        In Notion, create a connection (**Settings → Developer → Open developer tools → + New connection**, with **Access token** authentication) and copy its token. It starts with `ntn_` or `secret_`.
      </Step>
      <Step>
        Share the pages you want synced: open a top-level page, click **•••  → Connections**, and add your connection. Sharing a page also shares its subpages, so one top-level parent is usually enough. You control the scope by sharing or unsharing pages in Notion.
      </Step>
      <Step>
        In answerLoops, go to **Integrations → Notion**, paste the token, and click **Connect**.
      </Step>
      <Step>
        On the **Manage** tab, click **Sync now** in the **Notion workspace** panel. Each Notion page, and each row of a shared database, is converted to text, split into sections, and embedded like every other source.
      </Step>
    </Steps>

    Re-syncing replaces the previous Notion content. The workspace shows up as one entry named **Notion workspace**, and there is no environment variable to configure because Notion is set up per workspace.

    <Callout type="warn">
      Notion content imports **unpublished**. It is searchable from the dashboard, but it is not used to answer customer questions or served to the website widget until you click **Publish to widget** in the Notion panel. Every other source publishes automatically on import; Notion is the exception because workspace docs are often internal drafts. Your publish choice is kept across re-syncs, and **Unpublish** reverses it.
    </Callout>
  </Tab>
</Tabs>

GitHub and Notion syncs run as background jobs. The Manage tab shows each one as **Queued**, then **Syncing** with a progress count, then done, and you can leave the page while it runs. Starting a sync for a source that is already syncing does nothing; the running job finishes on its own. Each sync builds its replacement alongside your live content and swaps it in only when complete, so a failed sync leaves your existing content in place.

### Write an answer by hand

Not everything the assistant should know comes from a document. Product details, policies, and "how we actually do it" answers often live in someone's head. The **Write an answer by hand** form at the top of the Manage tab lets you write them down directly.

<Steps>
  <Step>
    Enter a **Question or title**, such as "Do you ship to Canada?"
  </Step>
  <Step>
    Write the **Answer or context** the way you would tell a customer.
  </Step>
  <Step>
    Click **Add to knowledge base**.
  </Step>
</Steps>

<Callout type="warn">
  The article is published immediately, with no draft step, so anything you write is visible to customers through the assistant. Leave out names, account details, and anything internal. If you want a second pair of eyes first, use the [Review queue](#review-queue) instead.
</Callout>

Only workspace owners and admins can add articles this way. The title can be up to 500 characters and the answer up to 8,000. Each article is indexed when it is saved, so adding needs an AI provider; if none is connected, the form tells you to add one in **Settings → AI Model**. Adds are limited to 30 every 10 minutes per workspace.

### Promote a resolved ticket

When a ticket is resolved with a good answer, turn it into an article so the AI can reuse that answer for similar questions.

<Steps>
  <Step>
    Open a ticket that is resolved and has an answer.
  </Step>
  <Step>
    In the **Knowledge Base** panel on the ticket, click **Promote to KB**.
  </Step>
  <Step>
    The question and answer are saved as a new article, and the panel changes to **In knowledge base**.
  </Step>
</Steps>

Only owners and admins can promote tickets, and promoting shares the same 30-per-10-minutes limit as writing by hand. A promoted article lists the ticket it came from, and it appears on the Knowledge coverage tab under **Promoted from resolved tickets**.

**Search** looks for articles by meaning rather than exact words. Asking "how do I reset my password" surfaces an article titled "Account recovery steps" even though the words differ, and each result shows a match percentage. To return to the full list, click the **×** in the search field or **Clear**.

If semantic search is unavailable, for example because no AI provider is connected or the provider's key is invalid, search falls back to exact text matching and an amber banner reads **Keyword search only**.

The **Sources** list shows everything you imported. Each row has a type tag (`url`, `pdf`, `docx`, `md`, `txt`, `csv`, `github`, `github-discussion`, or `notion`), the file name, page address, or repository, and a count of chunks and size. A source marked **Unpublished** is indexed and searchable from the dashboard but held back from customer-facing answers and the website widget.

To remove content, tick one or more sources or articles, click **Delete selected**, and confirm. Deleting a source also deletes the articles imported from it. Only owners and admins can delete.

## See what the assistant knows

The **Knowledge coverage** tab shows exactly what your chat assistant can answer from, so nobody is surprised by what it does or does not know. It is also linked from **Settings → Widget**.

- **Counts.** **Live articles**, **Sources**, **Unpublished**, and **Not searchable**.
- **Titles by source.** Every article title, grouped by where it came from: each file or imported page, synced sources, **Promoted from resolved tickets**, and **Added by hand**.
- **Status per article.** An article is live when it is published and searchable. **Unpublished** articles are kept private and the assistant does not use them until you publish them, which suits internal documents. **Not searchable** articles have no search index entry, usually because embedding failed during import, or they were indexed with an embedding model other than the one your workspace uses now. Articles on an older model are re-indexed automatically after you switch models; for a failed import, re-import the source.
- **Try a customer question.** Type a question and click **Check**. The tab runs the same lookup the chat widget uses and shows which articles the assistant would draw on, with a match score, or tells you that nothing covers it. If semantic search is unavailable, it says so instead of guessing.
- **Supplied as context.** Next to each article, how often it was handed to the assistant (details below).

If a question does not closely match any live article, the assistant answers from general knowledge instead, and that answer can be wrong. Use this tab to find those gaps before your customers do, then add or edit an article to cover them.

## Review queue

The **Review** tab turns questions your knowledge base could not answer into new articles, with a person checking every one before it goes live. It requires the Pro plan or above and is visible to owners and admins only, because items contain text typed by customers and visitors. Other team members see a short notice.

When the assistant answers a question that nothing in your knowledge base (or your team's earlier answers) covered, the question lands in the queue instead of disappearing:

- **Support tickets** from your connected channels are added after the assistant has replied, so capturing a question never delays an answer. If the assistant's draft fully answered the question, it comes along as a starting point. If not, the item is marked **No usable answer — write one** and you write it.
- **Website chat widget** questions are added when no article matched. The queue shows the question and the answer the assistant gave, never the visitor. Email addresses, phone numbers, and long digit runs are replaced with markers before the text is stored, and widget items are labelled as visitor-supplied text.

When the same question comes in again, the existing item's counter goes up (**Asked 4 times**) instead of adding a duplicate, and the most-asked questions are listed first.

<Steps>
  <Step>
    Open the **Review** tab. The **To review** list shows pending items; **Approved** and **Rejected** show past decisions.
  </Step>
  <Step>
    Edit the **Question** and the **Answer**. Remove names, account details, and anything else that was only meant for the person who asked.
  </Step>
  <Step>
    Click **Approve and add to knowledge base**. The text is saved as a new article and starts answering questions straight away. Or click **Reject** to dismiss it; a rejected item can be moved back to review with **Move back to review**.
  </Step>
</Steps>

Nothing in the queue is searchable or shown to customers until you approve it. The **Review** tab shows how many items are waiting. Each workspace holds up to 500 unreviewed items at a time; when the queue is full the tab says so and new questions are not captured, so clear it regularly.

## Verifying an article

An article can be marked as verified: an owner or admin checked it and found the answer still correct. On the **Manage** tab, each article shows where it stands, always in words:

- **Never verified.** Nobody has checked it. Every article starts here, including every article that existed before verification was introduced.
- **Verified on a date by a person.** Someone checked it, and its question and answer have not changed since.
- **Changed since last verified.** It was verified, but its question or answer has been edited or refreshed since, so the check no longer applies. Verifying it again clears this.

To verify an article, choose **Mark as verified** (or **Verify again**) and add an optional note, for example the product version you checked it against. The note can be up to 500 characters.

A few things to know about what verification means:

- Verification applies to the exact wording that was checked. Any change to the words, whether by a person, a ticket refresh or a sync, makes the article read as changed since last verified. Reflowing text or adding trailing whitespace is not a change.
- Imports and syncs never verify an article and never clear a verification on their own. A page rewritten by a sync with new content simply reads as changed since last verified.
- Age alone never makes an article wrong. A verification of unchanged text stays valid however old it is, and verification has no effect on whether the assistant uses an article.
- If the person who verified an article is later removed from the team, the date and note stay and the name is dropped.
- Each verification is also recorded in the article's history.

## More details

<Accordions>
  <Accordion title="Limits at a glance">
    | Limit | Value |
    |---|---|
    | Articles per workspace | 2,000, shared by every source. Once full, further adds, imports, and approvals are declined with a message, even if several people add at the same moment. |
    | URL import, per run | Up to 25 new pages, 150 sections, and about 600,000 characters in total across all pages. Section titles are shortened to 300 characters. |
    | URL import rate | 10 imports every 10 minutes per workspace |
    | File upload | 10 MB per file, 2 MB of extracted text, 300 PDF pages, up to 200 sections per file, 10 uploads every 10 minutes. File names are shortened to 200 characters. |
    | GitHub sync | Up to 100 Markdown files, plus up to 300 answered Discussions |
    | Write or promote | 30 every 10 minutes per workspace |
    | Review queue | 500 unreviewed items |

    If a site import reaches its per-run limit, the pages not yet reached stay un-imported and the next run continues from them.
  </Accordion>
  <Accordion title="Changing your embedding model">
    If the embedding model behind your knowledge base changes, answerLoops re-embeds your content in the background from what you already added. Search keeps working throughout, and you do not need to re-upload anything. An article you edit while the re-index runs is processed again before it goes live. The re-index stops with a clear message if the chosen embedding model produces vectors of a size the knowledge base cannot store.
  </Accordion>
  <Accordion title="Who added an article">
    When a team member adds an article by hand (including from the Knowledge Gaps page), promotes a resolved ticket, or approves a question from the review queue, answerLoops records that person as the article's creator. This is separate from whoever originally answered the ticket.

    Some articles have no recorded creator, and that means unknown, not nobody. Articles that existed before this was recorded keep an unknown creator, and articles made by file upload, URL import, or a synced source are created by the import itself. Refreshing a ticket's article later does not change who is recorded as its creator, and removing a team member keeps their articles.
  </Accordion>
  <Accordion title="Article history">
    answerLoops keeps an append-only history for each article. It records when an article was created, when a resolved ticket was promoted into one, when its question or answer was changed, each time a person verified it, and each review decision on the question that became the article: approved, rejected, or reopened. Every entry notes who did it and where it came from: added by hand, promoted from a ticket, the review queue, a file or URL import, or a synced source.

    - Changes made by a sync or import are recorded as automated, with no person attached. A sync that rewrites a page with the same content adds nothing.
    - Only a change to the words counts as an edit. Reflowing text or adding trailing whitespace does not.
    - The history stores a fingerprint of the question and answer at each moment, never a copy of the text, so it does not keep old wording and it is unaffected by the review queue's text retention.
    - Articles that existed before the history was introduced start with no entries. Nothing is reconstructed or guessed for them.
    - Deleting an article deletes its history, and deleting a team member keeps their entries with the person removed.
  </Accordion>
  <Accordion title="Article usage (Supplied as context)">
    The Knowledge coverage tab shows each article's **Supplied as context** count: the total recorded (up to 400 days, with older counts removed automatically) and the last 30 days. An article is counted when it was among the matches handed to the assistant as context for an answer that was actually produced: a reply in the website chat widget, a drafted reply to a support ticket, a Discord `/ask` answer, or an answer generated through the Agent API. Searching the knowledge base, running a [simulation](/docs/product/simulation), and bug reports or feature requests (which are never answered from the knowledge base) are not counted.

    - The count means the article was given to the assistant, not that the reply quoted it. The assistant decides what to use.
    - Only a number per article per day is stored. The question, the visitor, and the ticket are never recorded with it.
    - When usage data loads, an article with no recorded usage shows zero. If it cannot be loaded, the tab shows **Usage unavailable** instead of treating the missing data as zero, and coverage information remains available.
    - Deleting an article, or the workspace, removes its counts.
  </Accordion>
  <Accordion title="Review queue text retention">
    The text of rejected items is removed, and the text of approved items is removed 90 days after review (the approved article keeps its own copy). The item and its counter stay so a repeated question is still recognised.
  </Accordion>
  <Accordion title="Where the data lives (self-hosted)">
    Articles and source chunks are stored in the `kb_articles` and `kb_sources` tables in PostgreSQL. Questions waiting in the review queue are stored in `kb_review_items` until they are approved or rejected, and the per-article answer counts are stored in `kb_article_usage`. They persist across Docker restarts as long as you retain the `postgres-data` volume.
  </Accordion>
</Accordions>

<Callout type="warn">
  Never run `docker compose down -v`. The `-v` flag deletes all Docker volumes, which permanently removes your KB articles, tickets, and all other data. Use `docker compose down` (without `-v`) to stop the stack safely.
</Callout>

This reference describes the main records used by answerLoops. The schema definitions are in `lib/db/schema.ts`; migrations define changes applied to an existing database.

## Workspace and access

| Records | Purpose |
| --- | --- |
| `orgs` | Workspace identity and configuration. |
| `users`, `memberships` | User accounts and their workspace roles. |
| `invitations` | Pending team invitations. |
| `api_keys` | API key metadata and permissions. |

## Support conversations

| Records | Purpose |
| --- | --- |
| `tickets` | Question, source, category, priority, status, and AI draft state. |
| `ticket_replies` | Replies associated with a ticket. |
| `ticket_events` | Recorded changes in the ticket's history. |
| `ticket_links` | Relationships between tickets. |
| `ai_assessments` | Results of AI assessment. |
| `ticket_feedback` | Positive and negative answer feedback. |
| `csat_ratings` | Customer satisfaction ratings. |

## Knowledge

| Records | Purpose |
| --- | --- |
| `kb_sources` | Imported source metadata. |
| `kb_articles` | Searchable knowledge articles and their publication state. |
| `kb_sync_jobs` | Progress of background imports. |
| `ticket_embeddings` | Search representations associated with tickets. |
| `faq_snapshots` | Generated FAQ content. |

## Product feedback

| Table | Contents |
|---|---|
| `product_feedback` | Feedback entries from the in-app widget: vote, text, moderation status, and the team's reply. Shared across workspaces; each row records its author's workspace for display. |
| `product_updates` | The "what's new" feed shown on the widget's Updates tab. |

Changes to the feedback and updates tables notify connected dashboards so the widget updates live.

## Configuration and billing

Integration records store channel configuration. Each integration's shared secret is stored as a SHA-256 digest (`bot_secret_hash`), which is what inbound requests are matched against, together with an encrypted copy (`bot_secret_enc`) for the channels that must read it back to configure a remote webhook; lookups are always made for one platform at a time. Google Chat keeps its one-time connect code in separate columns (`pairing_code_hash`, `pairing_code_enc`, `pairing_code_expires_at`) that are cleared when the space is paired. At most one enabled Slack, Discourse or Google Chat integration can hold a given workspace, site or space (`team_id`).

Message de-duplication is scoped to the workspace: `tickets` is unique on `(org_id, source_message_id)` and `email_messages` on `(org_id, rfc_message_id)`. Telegram tickets use `telegram:<chat id>:<message id>` as their source message id, because Telegram message ids repeat across chats; tickets created before that format keep the bare message id and are still recognised as duplicates.

`ai_configs` stores workspace model settings. `sla_configs` stores response and resolution targets per priority. Rows with a null `org_id` are the global defaults; a workspace that saves its own targets gets its own row (unique per `org_id` and `priority`, removed with the workspace). Deadlines for a ticket use the workspace's row for the ticket's priority and fall back to the default row. `subscriptions` records hosted-plan state, and `api_generations` records standalone answer generation for usage accounting.

Use application actions and documented APIs for routine changes. For self-hosted upgrades, apply the documented migrations and retain a tested backup. See [Upgrading](/docs/self-hosting/upgrading).

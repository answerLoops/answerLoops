# answerLoops — Architecture

> How every piece connects: from a community message to a deflected answer and a self-improving knowledge base.

---

## 1. One-paragraph thesis

A community member asks a question in Discord, Slack, GitHub Issues/Discussions, Telegram, email, the embeddable website widget, or via an AI agent over MCP/REST. The platform ingests it, triages it with AI, embeds it to find prior similar questions, drafts an answer grounded in the team's past answers and (optionally) the project's source code, grades that answer's confidence, and either **auto-answers** the community (high confidence) or **routes it to a human** (low confidence) with the AI's draft attached. Resolved answers feed back into the knowledge base so repeat questions get cheaper and faster over time. Staff manage everything from a multi-tenant, OAuth-gated web dashboard. Every AI call uses the org's own configured provider — OpenAI, Anthropic, Google, Groq, Mistral, or any OpenAI-compatible endpoint (including local models) — the platform has no hardcoded model dependency.

---

## 2. Ingest pipeline (the core flow)

Every channel funnels into the same pipeline (`lib/ingest/pipeline.ts`, `processCommunityMessage`), regardless of source:

| # | Step | Output |
|---|------|--------|
| 1 | **Validate + dedup** | reject already-processed messages |
| 2 | **Triage** | category, severity, priority (fast/cheap model pass) |
| 3 | **SLA deadlines** | response + resolve deadlines set by priority |
| 4 | **Create ticket** | row in `tickets`, notifies staff (in-app + optional email/push) |
| 5 | **Embed** | vector stored for semantic search |
| 6 | **Find related** | prior similar tickets/KB articles surfaced |
| 7 | **Agent answer** | draft grounded in KB + prior answers, optionally + connected GitHub repo source |
| 8 | **Confidence review** | a separate AI pass grades the draft's confidence |
| 9 | **Deflect or route** | confidence above threshold → auto-post; otherwise → human review queue with the draft attached |

If any AI step fails, the ticket still gets created and defaults to the human queue — a pipeline failure never silently drops a question, and never auto-deflects on error.

Each org can bring its own AI provider key (Settings → AI Model); the platform falls back to a shared key if none is configured.

---

## 3. Multi-channel ingest

| Channel | Notes |
|---|---|
| Discord | 1-click OAuth or manual bot token; an org can connect any number of Discord servers |
| Slack | 1-click OAuth or polling mode (no webhook required) |
| GitHub | Issues + Discussions ingested as tickets; answered Discussions also sync into the KB directly |
| Telegram | Webhook-based |
| Email | Zero-setup platform-hosted inbound address by default, or bring-your-own provider |
| Website widget | Embeddable `<script>` chat widget |
| MCP / Agent API | AI agents (Claude, Cursor, custom bots) call the platform as a tool via `POST /api/mcp` (JSON-RPC) or `/api/v1/agent/*` (REST) |

An in-process set of answer ids stops a repeated callback while one is in flight, and the storage's unique key stops it after. The per-answer cost is computed from reported tokens and logged when over `SUPPORT_COST_CEILING_MICROS`, not enforced. Shadow run and go/no-go gate (#446): results are stored and shown to no one until a go. The owner-approved targets live only in `lib/kb/support/targets.ts` (`SHADOW_TARGETS`: precision of `supporting` at least 0.90 for supports findings, supporting articles and supporting answers, at least 200 human-labeled pairs, false-negative rate at most 0.30, `SUPPORT_COST_CEILING_MICROS` per answer; `inconclusive` and `not_assessed` never count as supporting; labelers limited to `workspace_owner`/`approved_maintainer`, labeling blind). `pnpm support:shadow` (`scripts/support-shadow.ts`, commands in `lib/kb/support/shadow-cli.ts` with injected IO, pure logic in `lib/kb/support/shadow.ts`) has three commands: `sample` reads one workspace through `getShadowPool` and `getShadowExcerpts` (`lib/db/queries/kb-support.ts`, scoped by org id and method version; only claim findings of completed assessments with both excerpts unexpired; text is read only for the chosen ids), refuses with excerpt storage off or too few excerpts, draws a seeded sample stratified by the judge's label (proportional, largest remainder, at least one per non-empty label) and writes a blind labeling file (item id, claim excerpt, passage excerpt only, order shuffled across strata) plus a separate key (judge label, article and answer state, a case type derived from the rows, population counts, cost per answer from stored tokens); `template` writes the labels schema; `report` validates labels against the key (role, blind attestation, sample id, known items), joins them, reuses `labelMetrics` from `eval.ts`, measures two-reviewer agreement (percent and Cohen's kappa; disagreeing items stay unresolved), and ends with GO only when every target is met, otherwise NO-GO with what is missing. The unit is a stored claim finding, so judge `none` pairs (no row) are never sampled and the false-negative rate covers stored findings only. Output never includes excerpt text; files are written mode 0600. No migration and no UI. |

## 5. Web app surface

- **Auth** — Auth.js v5, Google OAuth. Sign-in is one action for new and returning people (every marketing button leads to `/login`) and is refused for an email the provider has not verified. Provisioning records the user (provider account id, last sign-in) and creates a workspace for a new one. The access gate in `auth.ts` then holds any account without a recorded terms acceptance on `/accept-terms`; accepting it (`lib/actions/terms.ts`) records the terms version and the optional marketing opt-in, and starts the card-free 14-day trial through `lib/billing/trial.ts`, once per person via the `trial_claims` ledger. Existing accounts are recorded as having accepted at sign-up by migration 0067. `auth.ts`'s `PUBLIC_PATHS` allowlist gates which routes skip session auth (self-authenticating webhooks, public marketing pages); everything else requires a session and is scoped to the caller's org. A URL that matches no website, platform, API, widget or public route gets a real 404 from the same gate rather than the sign-in redirect (`lib/marketing/known-routes.ts`); every route folder under `app/` must be classified, and `tests/unit/route-classification.test.ts` enforces it.
- **Dashboard** — live overview, tickets (list + detail with AI draft/confidence/related questions/SLA), knowledge base, analytics, FAQ auto-generation, simulation/dry-run mode, team management, billing, settings (channel integrations, AI model config, widget embed).
- **Chat widget embed** — `public/widget.js` is the loader on a customer's page. On load it calls the public `GET /api/widget/config?id=<token or slug>` (`app/api/widget/config/route.ts`), which resolves the id to the workspace's current token (`getOrgByWidgetToken` / `getOrgByWidgetSlug`) and returns that token plus display settings (`lib/widget/display-settings.ts`, limited by plan on the server): the window size, the launcher bubble color (the workspace's brand color on a plan with customization, otherwise the app blue) and the icon color that reads best on it. The response carries nothing else, is readable cross-origin, is rate limited per address and per id, and is cached for 60 seconds (`s-maxage`, so a rotated token or changed slug reaches pages within about a minute; throttled or failed answers are `no-store`). Unknown, expired or malformed ids get the default look and no token, never an error. The loader gives up after 2 seconds and falls back to the id as given, so a token snippet behaves as before; a slug that cannot be resolved loads nothing. The chat panel is then the iframe `/widget/<token>`, created the first time the visitor opens the bubble rather than when the page loads (and loaded again if the panel is reopened after the frame is more than four minutes old), where the Referer-based allowed-domains check and the render-token minting still happen, unchanged: the slug adds a name for the token, not a new trust path. The route is excluded from the session proxy in `proxy.ts` so the response stays cacheable. The chat route builds the model's instructions in `lib/widget/instructions.ts` from the workspace row the token resolved to, never from the request: in `knowledge-base-only` scope the fallback to general knowledge is replaced by a rule to answer only from the retrieved articles (which also declines unrelated requests), the owner's guidance note is added after it, and any scope value other than an explicit `general` gets the narrower instructions. The query layer reads an unrecognised stored scope as `knowledge-base-only` and re-cleans the note on read. **Appearance:** `lib/widget/appearance.ts` holds the limits (title 60 characters, welcome message 200), the plain-text cleaning, the strict `#rrggbb` color check, the WCAG-contrast choice of white or dark text, and `brandPalette()`, which turns the brand color into the `--brand-*` tokens. The settings actions (`saveWidgetAppearanceAction`, `resetWidgetAppearanceAction`) are owner/admin only and re-check the plan on the server; the query layer re-cleans every value on read. The chat panel page (`app/widget/[widgetToken]/page.tsx`) applies the title, welcome message and palette only when the workspace's plan includes customization, and the panel sets the tokens on its root element, with text on brand backgrounds drawn by the `.text-on-brand` class. The public config lookup carries the bubble color only, never the title or welcome message. **Conversation kept in the browser:** `lib/widget/transcript.ts` saves the visible conversation (visitor messages, replies and card results) in the visitor's own `localStorage` under `al_chat:<widget token>`, newest 40 messages or about 200 KB, forgotten a day after its last message, and restores it when the chat mounts (read through `useSyncExternalStore`, so the server-rendered page and the first client render agree). Every stored message is re-validated on read and nothing is sent anywhere to restore it; the server's own memory of the thread stays keyed by the visitor id. The thread is trimmed to the newest 48 messages before each send to stay inside the chat endpoint's message limit. The header's **New chat** button clears the saved conversation and gives the visitor a new id so the server starts a new thread too. When the chat call is refused with HTTP 403 (the page's short-lived pass ran out while the chat sat open) the panel holds the question in `sessionStorage`, reloads itself, restores the conversation and sends the question once; a second refusal within a minute shows the "timed out" prompt instead, as does blocked storage. **Our own pages:** the same widget is embedded on `/docs` and on the marketing home and pricing pages through `components/site-chat-widget.tsx`, which renders only when `SITE_CHAT_WIDGET_ID` (a widget public name or token, validated by `siteChatWidgetId()` in `lib/site.ts`) is set. It is read per request, not at build time, so changing it needs no rebuild; every page that mounts it is already rendered per request. It is never mounted inside the signed-in app. `MarketingPage` takes an opt-in `chat` prop, off by default.
- **Follow-up suggestions** — `lib/widget/follow-ups.ts`. When a workspace is on a plan with `white_label_widget` and has not switched them off (`followUpsAvailable`), the chat route adds the follow-up paragraph to the instructions (`lib/widget/instructions.ts`) and registers a sixth genui tool, `show_follow_ups` (`lib/widget/genui-tools.ts`); otherwise the assistant is never told about them and the tool does not exist. The tool's `execute` keeps only the questions the workspace's knowledge base can answer (`groundFollowUps`: the same embedding and `getKBContext` search and match threshold the chat uses, run side by side with a 4-second limit each, skipped in mock mode) and shows nothing when fewer than two remain. In the panel (`app/widget/[widgetToken]/widget-chat.tsx`, `lib/widget/follow-up-thread.ts`) only the newest reply's suggestions are live: they are hidden once the visitor types or sends a message, when the same reply carries another card, and for any tool call that came from a conversation restored from the visitor's browser.

Members up-vote with `voteProductFeedbackAction` in `lib/actions/product-feedback.ts` (membership required, rate-limited; it sets the wanted state rather than toggling, and one `INSERT ... ON CONFLICT` statement in `setProductFeedbackVote` refuses unapproved or own entries and makes a repeated add a no-op). The widget highlights the sort the list on screen was fetched with, so a failed sort request never leaves the button and the list disagreeing. Live: triggers on `product_feedback`/`product_feedback_votes`/`product_updates` fire `pg_notify('product_feedback_changed')`, `/api/events/stream` LISTENs and forwards a payload-less `feedback_changed` to *every* stream (unlike the org-filtered `data_changed`), and the widget refetches via the shared `lib/live-events` connection — so a row written by out-of-app operator tooling reaches open dashboards with no call back into the app. The widget collects no usage data: the only thing it sends is feedback a member chooses to submit, and the only thing it keeps about a visit is the last update id seen, in that browser's local storage. First-visit seed quote is inserted at boot only when enabled.
- **Marketing site** — landing page, `/pricing`, comparison pages, docs links — all pre-auth, public.
- **Docs site** — Fumadocs under `app/docs`, reachable on every deployment (it is deliberately not behind the marketing gate). The layout renders per request (`export const dynamic = 'force-dynamic'`) because the Changelog link at the foot of the sidebar (`components/docs/docs-sidebar-footer.tsx`, also shown in the mobile drawer) follows `DEPLOYMENT_MODE`, which is only known at request time; its address comes from `resolveChangelogUrl()` in `lib/marketing/changelog-link.ts`, which the dashboard sidebar's "What's new" also uses, and is left out on a self-hosted install, which serves no `/changelog`. The `Cache-Control` rule for `/docs/:path*` in `next.config.ts` still applies to these responses, so the shared cache serves most hits. `tests/unit/docs-layout-changelog.test.tsx` pins the per-request behavior.
- **Blog** — `content/blog/**/*.mdx`, a second Fumadocs collection alongside the docs one (`source.config.ts`'s `blog` export, loaded via `lib/blog/source.ts`/`lib/blog/posts.ts`). Flat under `/blog/<slug>` regardless of topic (thought leadership, an integration writeup, a comparison) — `category` in frontmatter groups posts on the index page instead of the URL. Rendered through the marketing site's own layout (`MarketingPage`/`PageHero`), not the docs sidebar shell. A post's cover image is either supplied in frontmatter or generated on request from its title+category by `app/blog/[slug]/opengraph-image.tsx`, so publishing a new SEO post never blocks on producing an image. A post can also set `canonicalUrl` in frontmatter to point its `<link rel="canonical">` at another URL — syndicated content, or a near-duplicate of one of our own posts — instead of the self-canonical every other page gets by default (`lib/marketing/metadata.ts`'s `publicPageMetadata`). Listed in `app/sitemap.ts` dynamically (new posts need no code change) and intentionally left out of `public/llms.txt`'s curated links (only `/blog` itself is listed there; individual posts are unbounded).

## 7. Deployment

- Multi-stage `Dockerfile` (deps → build → runner, no build toolchain in the final image), non-root user.
- Two services: **app** (dashboard + API, `pnpm start`) and **bot** (Discord gateway listener + background sweeps, `pnpm bot:start`). The bot also runs the maintenance sweeps — org purge, stuck-ticket recovery, the hourly **trial-ending reminder** sweep (calls `POST /api/billing/trial-reminders/run` with `BOT_SECRET`; the app claims each 3-day/1-day notice in `subscriptions.trial_reminder_*_sent_at` and emails the owner a checkout link), the **website chat lead email** sweep (every 5 minutes, calls `POST /api/widget/lead-notifications/run` with `BOT_SECRET`; a new lead is emailed to the workspace's owners and admins straight away by `lib/widget/lead-notifications.ts` when the workspace's window is open, otherwise it waits in `widget_leads` with `notified_at` NULL and this sweep sends the waiting leads together, up to ten listed and the rest counted; nothing is sent when no email service is configured), and the **KB sync worker**, which claims rows from `kb_sync_jobs` and drives each one by calling `POST /api/kb/sync-jobs/run` on the app with `BOT_SECRET`. Notion/GitHub KB syncs are enqueued (by "Sync now" and the GitHub push webhook) rather than run inline in those requests. The worker is NOTIFY-driven, not polling: a `kb_sync_jobs` trigger fires `pg_notify('kb_sync_job_queued', id)` on every enqueue and requeue, delivered over the bot's existing single-connection LISTEN socket (the same one used for `config_changed`/`member_joined`/`data_changed`); a coarse 5-minute sweep remains only as a safety net for a missed notification or a stuck `running` row. An unconditional short-interval poll here previously kept the database compute from ever autosuspending.
- `docker-compose.prod.yml` (self-hosted, both services from the one image) for production; `docker compose up` (dev target) for local development with a local Postgres.
- Migrations run automatically on startup — no manual migration step.
- The `Dockerfile` / compose files above are the self-hosted path. A PaaS deploy builds from the repo instead — Railway builds each service from the `Dockerfile`. Both services' deploy settings (build, start command, health check, restart policy) live in `.railway/railway.ts`, Railway's Infrastructure as Code, which replaces the deprecated `railway.toml` files. That file is not read at deploy time: changes reach Railway only when a maintainer runs `railway config apply`. See `docs/self-hosting/` for the full self-host guide.

## 8. Security posture

- Every pull request is scanned before merge: Cycode (dependencies, secrets, SAST, IaC, licenses) and Zizmor (GitHub Actions workflow audit for script injection/unpinned actions/over-broad permissions). The published image is scanned with Trivy and Snyk.
- Per-org data isolation is enforced at the query layer, with regression tests (`tenant-isolation*.test.ts`, `no-default-org.test.ts`) that fail if an org filter regresses.
- Secrets (bot tokens, AI provider keys) encrypted at rest.
